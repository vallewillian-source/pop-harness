# Contributing to POP Harness

Thanks for wanting to help. This guide explains how to set up your environment, what to run before opening
a pull request, and what we expect from a contribution. If anything here is confusing or out of date, that
is already a useful contribution: open an issue or fix the text.

By taking part, you agree to the [Code of Conduct](CODE_OF_CONDUCT.md).

> **Language.** Issues, pull requests and discussions are welcome in English or Portuguese. The code,
> identifiers, comments and most of the documents under `docs/` are in Brazilian Portuguese (domain terms
> such as `conversa`, `turno`, `org`). Keep the language of the code you are changing; new top-level
> project files (README, guides, templates) are in English. Translations of `docs/` are welcome.

## Before you start

| I want to... | Do this |
|---|---|
| Report a bug | Open a [bug issue](https://github.com/vallewillian-source/pop-harness/issues/new/choose) with steps to reproduce. |
| Suggest an improvement | Open a proposal issue **before** writing code, so we can agree on the design. |
| Ask a usage question | Use [Discussions](https://github.com/vallewillian-source/pop-harness/discussions). See [`SUPPORT.md`](SUPPORT.md). |
| Report a security flaw | Do **not** open a public issue. Follow [`SECURITY.md`](SECURITY.md). |
| Fix something small (typo, test, docs) | Open the pull request directly. |
| Pick a task | Look for issues labelled `good first issue` and `help wanted`. Comment that you are taking it, so nobody duplicates the work. |

Changes that alter an **API contract, a file format, the database schema or the design of a module** need
an issue approved by a maintainer before the pull request. This is so you do not spend time in a direction
we cannot accept.

## Set up the environment

You need Linux, a C compiler (`gcc` or `clang`) and [rustup](https://rustup.rs). The Rust version
(`1.100.0`) is pinned in `rust-toolchain.toml`, and `rustup` installs it on first use.

```bash
git clone https://github.com/<your-user>/pop-harness.git
cd pop-harness
cargo build --workspace
```

Verification tools (once):

```bash
cargo install cargo-deny cargo-audit --locked
```

To work on the Console (React and TypeScript) you also need Node 22.18 or newer and pnpm. See
[`DEVELOPMENT.md`](DEVELOPMENT.md).

## What to run before opening a pull request

The single command is:

```bash
bash scripts/ci.sh
```

It runs, in order: build-cache pruning, the Console build and API client check (skipped if
`console/node_modules` does not exist), `cargo fmt --check`, `cargo clippy` with `-D warnings`, build,
tests, an ARM64 check of the crates without C code, `cargo deny` and `cargo audit`. At the end it prints
`CI LOCAL: OK` or the number of checks that failed.

To iterate faster, run only what you touched:

```bash
cargo test --locked -p poph-retention          # one crate
cargo fmt --all                                 # format
cargo clippy --workspace --all-targets -- -D warnings
```

Some contract tests depend on files from outside this repository (the Element frontend) and are ignored by
default. If you have those files, run `cargo test -p poph-matrix --test contrato_frontend -- --ignored`
with `POPH_ELEMENT_CONTRATO` pointing to `atendimentoRoom.ts`.

## Project rules

These rules come from decisions already made and are explained in [`AGENTS.md`](AGENTS.md) and
[`docs/DECISOES.md`](docs/DECISOES.md).

- **Secrets never leak.** Keys come only from the environment and never go into a file, log, error
  message, API response or test with a real value. Use the `Sensivel` type for any sensitive value that
  passes through a log or error, and test with a canary value.
- **Isolation between orgs.** Every business table has `org_id` and every access filters by it. New code
  that reads or writes org data needs a test proving that org A cannot reach org B.
- **Layers.** `poph-types` depends on no internal crate; capability crates do not import `poph-server` or
  `poph`; `poph-agent` does not import `poph-matrix`. The table is in `AGENTS.md`. Cargo prevents cycles
  but not the direction of the layers: check it yourself when adding a dependency.
- **Database migrations.** Create a new file in `crates/poph-store/migrations/harness/NNNN_name.sql` and
  register it in `crates/poph-store/src/migracoes.rs` with the next number. **Never edit a published
  migration.** Changes are additive.
- **API contract.** Do not edit `console/src/api/schema.d.ts` by hand: it is generated by `poph openapi`.
  After changing a route, run `bash console/gen-api.sh`. CI fails if the file diverges from the server.
- **No `unsafe`.** The workspace uses `unsafe_code = "forbid"`.
- **New dependencies.** Each new crate needs a justification in the pull request and must pass
  `cargo deny` (permissive licences, no OpenSSL, crates.io registry only). Fewer dependencies is better.
- **The Jev chooses, the code validates.** A Jev failure must never become an effect. See `docs/JEV.md`.
- **Documentation with the code.** If your pull request changes a behaviour, update the matching document
  in `docs/` in the same commit.
- **Console.** No card inside a card, loading, empty and error states on every screen, and action buttons
  disabled while the request runs. See `console/UX_SPEC.md`.

## Code style

- Rust: `cargo fmt` and `clippy -D warnings`. Typed errors with `thiserror`; no `unwrap` or `expect` on a
  production path except for invariants the comment explains.
- Domain names in Portuguese (`conversa`, `turno`, `org`), as in the rest of the code.
- Comments explain **why**, not what. A comment that repeats the code goes.
- Tests live next to the code they cover. A new test must fail without your change.

## Commit messages

We use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/), with the crate or area as
the scope:

```
feat(poph-store): filter conversations by customer
fix(poph-evolution): ignore message event without external id
docs(cluster): explain reloading the map without a restart
```

Prefer small commits that compile. A pull request should do one thing.

## Open the pull request

1. Fork and create a branch from `main` (`feat/short-name` or `fix/short-name`).
2. Run `bash scripts/ci.sh` and confirm it passed.
3. Open the pull request and fill in the template. Say **what changes in practice**, **how you tested**
   and what you did **not** check.
4. Answer reviews in the thread. A maintainer may ask for changes or explain why we will not accept it;
   it is not personal.

We reply as maintainers have time. If a pull request sits for too long, feel free to nudge it in the thread.

### Origin and licence of contributions

The project is distributed under the [AGPL-3.0-or-later](LICENSE). By submitting a contribution you state
that you have the right to submit it and that it comes in under that licence. We use the
[Developer Certificate of Origin](https://developercertificate.org/) for this: sign off every commit with
`git commit -s`, which adds the line `Signed-off-by: Your Name <you@example.com>`.

## Contributions made with AI assistance

We accept them. You remain responsible for what you submit: read, run and understand what the tool wrote,
check that it did not copy code under an incompatible licence, and do not include anything you cannot
relicense under the AGPL. [`AGENTS.md`](AGENTS.md) describes the code map and working rules for agents and
people.

## Recognition

Contributors appear in the git history and in the release notes of each version in
[`CHANGELOG.md`](CHANGELOG.md).
