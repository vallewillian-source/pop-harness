# Isolated development Synapse with two Application Services (MX-01)

Environment for **MX-01** of the POP Harness Matrix module: a development Synapse that loads, at the same time,
**two Application Service registrations** — the one from POP Atende (Python), with fictitious tokens, and the
**new** one from the Harness (prefixes `ph_`). It serves as the base for MX-02 (spike of the Synapse contracts)
and, later, for the `#[ignore]` tests of the module.

- It is **not** the POP Atende dev (`popdev-synapse`, port 8008), **not** the ARM64 test machine and **not**
  production. Container, network, ports and data are its own; nothing here opens a port to the outside beyond
  `127.0.0.1`.
- Image: `matrixdotorg/synapse:v1.120.0` (already present on this workstation).
- Everything is outside git, in `~/.cache/poph-matrix` (can be changed with `POPH_MATRIX_DEV_DIR`).

## Start, stop, clean up

```bash
cd apps/pop-harness
bash scripts/matrix-dev.sh subir    # starts/restarts and waits for /_matrix/client/versions to respond
bash scripts/matrix-dev.sh parar    # stops the container, keeps the data
bash scripts/matrix-dev.sh limpar   # deletes ONLY what the script created
bash scripts/matrix-dev.sh url      # prints the URL and the server_name
```

(`subir` = start, `parar` = stop, `limpar` = clean, `url` = URL; these are the script's own commands and are kept.)

`limpar` removes the container `poph-matrix-synapse`, the network `poph-matrix-net` and the directory
`~/.cache/poph-matrix`. There is no Docker volume for the project (`/data` is a bind mount), so `docker volume ls`
looks the same before and after. No container from another project is touched.

## Parts

| Part | Where | Port |
|---|---|---|
| Dev Synapse | container `poph-matrix-synapse`, network `poph-matrix-net` | `127.0.0.1:18008` |
| Python registration (test) | `~/.cache/poph-matrix/data/registro-python.yaml` | default url `http://<IP-LAN>:18009` |
| Harness registration (new) | `~/.cache/poph-matrix/data/registro-harness.yaml` | default url `http://<IP-LAN>:18010/matrix` |
| `homeserver.yaml`, signing key, SQLite database | `~/.cache/poph-matrix/data/` | — |
| Fictitious tokens (for MX-02) | `~/.cache/poph-matrix/credenciais.env` (0600) | — |
| Registration templates (versioned, no token) | `apps/pop-harness/tests/matrix/*.template` | — |

Environment `server_name`: `matrix-dev.local`.

## The two registrations

| | Python (test) | Harness (new) |
|---|---|---|
| `id` | the one from the Python registration | `poph-matrix-dev` (template) or `poph-matrix` (generated by `poph`) |
| `sender_localpart` | `wa_as_bot` | `ph_as_bot` |
| exclusive users | `@wa_.*`, `@agt_.*`, `@em_.*`, `@test_.*` | `@ph_.*` |
| exclusive aliases | `#wa_.*`, `#em_.*` | `#ph_.*` |
| shared alias | `#dep_.*` (not exclusive) | `#dep_.*` (not exclusive) |
| `rate_limited` | `false` | `false` |

The namespaces are disjoint (PRD §12): the Synapse starts without conflict, and the log shows the two
`Loaded application service` lines (`id=poph-matrix-dev` and `id=popatende-python-teste`).

## Credentials stay out of git

The versioned templates only have the placeholders `__AS_TOKEN__`, `__HS_TOKEN__` and `__AS_URL__`. `subir`
generates **four new fictitious tokens on every run** (Python and Harness, `as_token` and `hs_token`), writes the
rendered registrations to `~/.cache/poph-matrix/data/` and the values to `~/.cache/poph-matrix/credenciais.env`
(0600). The script **prints no token at all**; whoever needs them (MX-02, tests) reads `credenciais.env`. None of
this goes into a commit: the directory is in `~/.cache`.

Why the rendered registrations are `0644`: the Synapse in the container runs as uid `991`, which is not the host
uid in this rootless Docker; a `0600` host file would be unreadable to it. The secrecy comes from the directory
(outside the repo, `credenciais.env` at 0600) and from the tokens being fictitious.

## Network: why the url uses the LAN IP

In this rootless Docker (slirp4netns `--disable-host-loopback`), the container **cannot reach the host's
`127.0.0.1`**. That is why the registrations' `url` values use the **LAN IP** (`hostname -I`) and high ports: 18009
for the Python AS and 18010 for the Harness AS. The Harness one has the `/matrix` path on purpose — MX-02 needs to
measure whether the Synapse calls `<url>/_matrix/app/v1/transactions/{txnId}` when the `url` has a prefix.

Nothing needs to be listening on those ports for MX-01: the Synapse only calls the `url` when there is an event for
the AS. For MX-02, start the receiver on ports 18009/18010 (or change the urls before starting):

```bash
POPH_MATRIX_DEV_URL_H="http://192.168.0.123:18010/matrix" bash scripts/matrix-dev.sh subir
```

Accepted variables: `POPH_MATRIX_DEV_DIR`, `POPH_MATRIX_DEV_PORTA`, `POPH_MATRIX_DEV_PORTA_PY`,
`POPH_MATRIX_DEV_PORTA_H`, `POPH_MATRIX_DEV_URL_PY`, `POPH_MATRIX_DEV_URL_H`, `POPH_MATRIX_DEV_IMAGEM`,
`POPH_MATRIX_DEV_REGISTRO_H` and `POPH_MATRIX_DEV_REUSAR_TOKENS` (the last two in the next section).

## Harness registration generated by `poph` (MX-21)

Up to MX-20 the Harness registration was the template rendered by the script. From MX-21 on, the CLI generates the
real one, with the environment's tokens:

```bash
# 1. starts (or restarts) the environment and writes the fictitious tokens to credenciais.env
bash scripts/matrix-dev.sh subir

# 2. generates the Harness registration with the SAME tokens, outside git
. ~/.cache/poph-matrix/credenciais.env
POPH_MATRIX_AS_TOKEN="$POPH_MATRIX_DEV_HARNESS_AS_TOKEN" \
POPH_MATRIX_HS_TOKEN="$POPH_MATRIX_DEV_HARNESS_HS_TOKEN" \
  ./target/debug/poph --config ~/.cache/poph-matrix/poph-matrix.toml matrix registro \
    --saida ~/.cache/poph-matrix/registro-gerado.yaml \
    --url "http://$(hostname -I | awk '{print $1}'):18010/matrix"

# 3. the Synapse now loads that file, reusing the tokens from step 1
POPH_MATRIX_DEV_REUSAR_TOKENS=1 \
POPH_MATRIX_DEV_REGISTRO_H="$HOME/.cache/poph-matrix/registro-gerado.yaml" \
  bash scripts/matrix-dev.sh subir
```

- `POPH_MATRIX_DEV_REGISTRO_H=<file>` makes the script copy a **ready** registration to
  `/data/registro-harness.yaml` instead of rendering the template. Use the command's own `--verificar` to find out
  whether it still matches the `[matrix]` section.
- `POPH_MATRIX_DEV_REUSAR_TOKENS=1` does **not** generate new tokens: it rereads `credenciais.env`. Without it, `subir`
  would change the tokens and the ready registration would be left with old `as_token`/`hs_token`.
- `poph matrix registro` writes with permission **0600** (the Synapse reads it through the `0644` copy that the
  script makes inside the container) and never prints a token. `poph matrix registro --verificar <file>` points out
  each divergence, naming the field (`url`, `sender_localpart`, `rate_limited`, `namespaces.users`,
  `namespaces.aliases`, `as_token`, `hs_token`).
- The `--url` is the address **where the Synapse reaches the Harness** (it is not the `homeserver_url`, which is the
  Synapse): here, the LAN IP with port 18010 and the `/matrix` path. Without `--url`, the variable `POPH_MATRIX_URL_AS`
  applies.
- The roadmap configuration is a `poph.toml` with only `[matrix]` (`habilitado = true`,
  `homeserver_url = "http://127.0.0.1:18008"`, `server_name = "matrix-dev.local"`), outside git.

Proof that the Synapse accepted the generated registration (MX-21): the log shows `Loaded application service` with
`id=poph-matrix`, `url=http://<IP-LAN>:18010/matrix`, `sender=@ph_as_bot:matrix-dev.local`, `rate_limited: False`,
and an authenticated `createRoom` call with the `as_token` from the file returns `200` with a `room_id` (a wrong token
returns `401 M_UNKNOWN_TOKEN`).

## How to check that it is running

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18008/_matrix/client/versions   # 200
docker logs poph-matrix-synapse 2>&1 | grep 'Loaded application service'                  # two lines
docker ps --filter name=poph-matrix --format '{{.Names}} {{.Status}}'                     # healthy
```

`subir` already does the first and prints the two `Loaded application service` lines. The container has the image's
own healthcheck (`healthy`).

## Element captures for the MX-31 acceptance

`scripts/aceite-matrix-element.mjs` takes the Element screenshots of the acceptance. It talks to Chrome through the
DevTools protocol (Node 22's native WebSocket), without Playwright. `scripts/aceite-matrix.sh` (step A12) runs it with
the right paths and variables; it can also be run by hand:

```bash
node scripts/aceite-matrix-element.mjs a1    <output> <room> <space> <directory>
node scripts/aceite-matrix-element.mjs final <output> <room> <space> <directory> [late-name-room]
```

- `a1` captures the room just created (with the customer's name) and the department's space **before** any transfer.
  It proves the room is born named and already inside the space.
- `final` captures the state after the agent's reply, the transfer, the reopening and the closing, the home and, when
  given, the room whose name arrived later (MX-32/MX-33).
- Files written to `<output>`: `a1-sala.png`, `a1-espaco.png` (for `a1`); `sala.png`, `espaco.png`,
  `sala-nome-depois.png` (when given) and `home.png` (for `final`); and `capturas.txt` listing them. On failure it writes
  `falha.png` and exits 1.
- Each mode has its own Chrome profile (`<directory>/chrome-profile-<mode>`), so the two passes do not share a profile.
  A session left in that profile is reused by the next run of the same mode.
- Before starting, leftovers from a Chrome killed by force are removed from the profile (`DevToolsActivePort` and the
  `Singleton*` files); otherwise the next run reads the previous port and fails to connect.
- Login: the account is the disposable development account of Synapse. If Element asks for device verification, the
  script follows "Não consegue confirmar?" → "Continuar" → password. Element itself is not changed.
- Banners that cover the screen ("Mais tarde", "Ok", "Dispensar") and the first-login modals ("Not now") are dismissed.
  None of them changes the app; they only get in the way of the capture.
- The Element texts above are matched literally. If Element changes its wording or language, these strings must change too.
- Environment: `CHROME_BIN` (default `google-chrome`), `ACEITE_ELEMENT` (default `http://127.0.0.1:18403`),
  `ACEITE_USUARIO` and `ACEITE_SENHA` (default: read from `<directory>/atendente.usuario` and `atendente.senha`).

## Limits of this environment

- No federation (`trusted_key_servers: []`), no TLS, no open registration.
- Disposable data: `limpar` deletes everything. Do not keep anything here that needs to survive.
- A Synapse reads the registrations only at startup: changing a token or a url requires running `subir` again.
- It belongs to MX-01/MX-21 (validation and tests). The real Harness registration is generated by
  `poph matrix registro` (MX-21), with real tokens, and requires restarting the environment's Synapse — never this
  script.

## Acceptance run (`scripts/aceite-matrix.sh`, MX-31)

The script is the phase 1 gate for the Matrix module. It starts a real `poph serve` against
the development Synapse (port 18008), with the NEW Harness registration and the OLD Python
registration loaded at the same time, fake Evolution and LLM servers, a real human agent on
Synapse and the current Element served locally. It does not do production, deploy, push or
code fixes. Tokens, passwords and phone numbers are never printed; values stay in 0600 files.

Usage:

```bash
bash apps/pop-harness/scripts/aceite-matrix.sh                  # full run
bash apps/pop-harness/scripts/aceite-matrix.sh --sem-element    # no screenshots
bash apps/pop-harness/scripts/aceite-matrix.sh --fase2          # includes acceptance A14 (phase 2)
bash apps/pop-harness/scripts/aceite-matrix.sh --manter         # keeps the working folder
```

Variables: `POPH_ACEITE_DIR` (working folder, default `~/.cache/poph-aceite-matrix`),
`CHROME_BIN` (browser for the screenshots, default `google-chrome`), `ACEITE_ESPERA_ESPACO`
(seconds the A6 check waits for the room to leave the old space, default 60).

Exit codes: 0 when every checked criterion passes, 1 when one fails, 2 when an environment
prerequisite is missing (Synapse, container, busy port).

Rules the run depends on:

- **Registration.** The run uses the Harness registration file of the environment as it is
  (the `url` ends in `/matrix`, which is the real path). It does not generate another
  registration, does not change the Synapse registration and does not restore anything at
  the end.
- **Admin token (MX-46).** It is not created by `matrix-dev.sh`. It lives in its own file,
  because `matrix-dev.sh subir` rewrites the credentials file on every run.
- **Phase 2 retention.** With `--fase2`, media retention is set to 1 day, only in the working
  folder of this run. The report says which value was used.
- **Room placement (MX-15).** The Harness writes `m.space.child` on the new space, sends the
  invites and only then records the room's space in `matrix_rooms.space_room_id`. A transfer
  uses that record as the "old space", so asking for it before the record exists leaves the
  room in two spaces, and no later pass fixes it. Measured in MX-50: the record arrives about
  1.5 s after `m.space.child`. The run therefore waits for the placement at creation before it
  transfers.
- **A6 (transfer moves the room).** The product enters the new space before it leaves the old
  one. That is intentional: a crash in between leaves the room in two spaces, never in none.
  The assertion requires both conditions together, with an explicit limit
  (`ACEITE_ESPERA_ESPACO`), and fails when the limit runs out. There is no fixed sleep.
- **Space check after transfer.** `fora_do_espaco` returns 0 when the space has no
  `m.space.child` for the room (Synapse answers 404 for a missing state event and 200 with `{}`
  for a removed child), 1 when the room is still there, and 2 when the state could not be read
  (transient error, 403). The 2 exists so a read failure is never taken for "the room left the
  space".
- **Room created in the department space.** A room created by the Harness enters the department
  space at creation (MX-31 fix). That check runs before the transfer, so A1 is proven without a
  trigger.
- **Human agent.** The human agent is a member of the space and joins the restricted room
  (`join_rules` is written at creation). The application-service bot writes with power level 50;
  a new agent would have 0.
- **Name arriving after the room (MX-32/MX-33).** The room is created with only the phone number,
  and the customer name comes in the next message. The run checks the room title, the
  `client_name` metadata and the ghost display name change, and checks that no new `m.notice`
  appears: changing a name is not a service event.
- **Phase 2 fixtures (MX-43 to MX-46).** The fixtures come from the auxiliary helper and contain
  no customer data. The Evolution fake serves media only for the known mimetypes. Expiration runs
  at server startup, so the server is restarted for that pass. A re-delivery of the same Element
  transaction makes Synapse return the same event without publishing it again.
- **MX-44 diagnosis.** The application service cannot impersonate the human user, so a download
  made with the service token and the agent's user id fails with the HTTP code the run reports.
- **Audio and video fixtures.** With `ffmpeg` installed they are real files. Without it, a
  minimal header is generated. Element shows "error downloading the audio" for header-only files,
  so the playback check is only meaningful with `ffmpeg`. The delivery path is the same in both
  cases.
- **Evolution fake logging.** It logs only the metadata of sent media (size, hash, mimetype),
  never the content.
