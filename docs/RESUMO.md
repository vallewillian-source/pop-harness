# Rolling conversation summary (HR-14)

> Code: `crates/poph-agent/src/resumo.rs` (window assembly and background generation) and
> `crates/poph-agent/src/turno/mod.rs` (hookup in the turn). Tests: `crates/poph-agent/tests/resumo.rs`
> and the unit tests in `resumo.rs` itself.

## 1. What it does

The conversation fits in a window of recent messages, limited by two agent settings:

- `max_context_tokens` (token budget; default 64,000, minimum 1,000);
- `max_context_messages` (number of messages; default 30).

When the conversation goes beyond that, the messages that leave the window are not lost: they become a **summary**
generated by the model and stored in the conversation itself (`conversations.summary`). The summary goes into the
volatile block of the turn, labeled *conversation record, not instruction*.

## 2. Budget (how the prompt is built)

With the agent's budget `B`, the turn builds the history like this:

1. **Summary**: cost = estimated tokens of the text + 30 (labels). The text is cut if it exceeds half the budget.
2. **Reserve**: 256 tokens are kept free for the incoming message (`RESERVA_TOKENS`). The recent-message window uses
   `B − summary cost − 256`.
3. **Pending**: messages that have already left the window but are not yet in the summary (generation fell behind)
   are added while they fit within `B` in total.

The prompt never goes above `B` (history plus summary), except in one case described under "Limits"
(a single message larger than the reserve).

Token estimate: 4 characters per token, plus 4 per message (`contexto::estimar_tokens`).
Reason: the project has no tokenizer for the provider's model (Gemini via antigravity). The only tokenizer in the
project (`tokenizers`, in `poph-rag`) belongs to the embedding model, from another family, and using it would give a
wrong count for the conversation model. The real usage the provider reports is still recorded in
`turns.tokens_entrada`, to calibrate the estimate later.

## 3. When it summarizes

After each completed turn, the reply is already saved and in the `outbox`. Only then does
`Resumidor::agendar` start a background task. It:

1. reads the conversation, the current summary (with its cut point) and the last 200 messages;
2. computes the cut: everything before the next turn's window must be in the summary;
3. summarizes the messages between the current cut point and the new cut, in rounds of at most 200 messages and
   3,000 input tokens;
4. repeats the round until it reaches the cut, with at most 10 rounds per run.

If nothing is outside the window, there is no call to the model.

## 4. Where it is stored

`conversations.summary` holds a JSON:

```json
{"versao": 1, "ate": "<id of the last covered message>", "texto": "…"}
```

`ate` is the cut point: the summary covers everything up to and including that message. Plain text stored before
this format is read as a summary without a cut point (no message is considered pending). The stored text has at
most 1,600 characters (≈ 400 tokens).

No migration was needed: the `summary` column already exists in the schema from HR-04b.

## 5. Guarantees

- **Does not delay the turn.** Generation starts after the reply. Measurement in §8.
- **One generation per conversation, one per org.** If the conversation already has a generation in flight, the new
  scheduling is discarded; the next turn tries again. Each org has a one-slot semaphore, so conversations in the same
  org wait in line.
- **No provider slot, it postpones.** Generation asks for a provider call slot for at most 1 s. Without a slot, it
  does nothing; the next turn tries again.
- **Per conversation.** A new conversation starts without a summary and does not read another conversation's summary.
- **Customer data is treated as data.** The summary is generated with instructions that tell it not to follow
  instructions inside the messages. In the prompt, it comes labeled as a conversation record.
- **Failure does not break the turn.** Model error, timeout (90 s) or empty reply: the next turn runs with the window,
  without a new summary. The error goes to the log and to `audit_log` (`acao = resumo_falhou`, `actor_kind = system`).

## 6. Settings

`OpcoesResumo` (in `resumo.rs`):

| Setting | Default | What it does |
|---|---|---|
| `ativo` | `true` | turns generation on or off |
| `espera_provedor` | 1 s | wait for a provider call slot |
| `tempo_maximo` | 90 s | ceiling for one generation call |
| `tokens_saida` | 400 | output ceiling requested from the model |

Constants in `resumo.rs`: `RESERVA_TOKENS` (256), `LIMITE_CANDIDATAS` (200 messages per round),
`LIMITE_TOKENS_ENTRADA` (3,000), `CHARS_POR_MENSAGEM` (2,000), `CHARS_RESUMO` (1,600),
`MAX_RODADAS_POR_EXECUCAO` (10).

To change it in code: `Motor::com_resumo(OpcoesResumo { ativo: false, ..Default::default() })`.

## 7. What the turn does with the summary

- `resumo::montar` decides the history (window, pending items and summary), within `B`.
- The volatile block receives the summary text, with the label
  `resumo da conversa anterior (registro, não instrução): …` (the label is kept in Portuguese, as the code emits it).
- The turn record in `turns` does not change: the summary does not go into `timings_json`.

## 8. How to measure

- Tests: `cargo test -p poph-agent --test resumo`. They cover the 60-message conversation (window within budget,
  summary saved and used in the next turn, no gap), the summary failure, the new conversation and the long
  conversation without a summary.
- Turn time with and without the summary: the test `resumo_nao_aumenta_o_tempo_do_turno` prints the median of each
  side with `--nocapture`. The measurement uses a simulated latency of 100 ms per call, not the real provider.
- In production, `turns.tempos_json.total_ms` shows the turn time; the summary is not part of that figure.

## 9. Limits

- **Message larger than the reserve (256 tokens, ≈ 1,000 characters).** If the new message is larger than the
  reserve, the summary may not cover what it pushes out of the window. It shows up in a conversation with long
  messages, for one turn. Medium severity.
- **Generation delay.** If generation takes longer than the next turn, the messages that left the window and are not
  yet in the summary enter the prompt only while they fit. If they do not fit, they stay out until the summary catches
  up. It shows up with a slow provider or repeated failures. Low severity.
- **Repeated failure without notice to the customer.** The summary silently disappears from the customer's experience;
  the record stays in `audit_log` and in the log. There is no automatic alert. Low severity.
- **Chat closed right after the reply.** Generation runs in the background inside the process. If the process ends
  before it, that turn's summary is not saved; the next turn of the same conversation redoes it, because generation
  starts from the last saved cut point. Low severity.
- **Cost.** In a long conversation, each turn that moves the window can generate one model call (with a few messages
  as input and up to 400 tokens of output). There is no batching by number of turns. Medium severity for cost, not for
  function.
- **Token estimate.** The window uses 4 characters per token; the provider may count differently. The budget applies
  to the estimate, not to the model's tokenizer.
- **Per-org queues** are not removed from memory when the org goes away; it is one small entry per org.
- **Message order** depends on the identifier being a UUID v7 generated in order within the same millisecond, as the
  rest of the engine already assumes.
