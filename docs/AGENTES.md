# Agents, instructions and composer (HR-09)

The administrative endpoints are implemented in [`api/agents.rs`](../crates/poph-server/src/api/agents.rs) and [`api/instructions.rs`](../crates/poph-server/src/api/instructions.rs). Agent flow assignments are handled in [`api/agent_flows.rs`](../crates/poph-server/src/api/agent_flows.rs).

> HR-09 deliverable. Covers the agent entity with the `V1` fields, the structured instructions, the
> composer (ported from POP Atende, the product the project originated from) and the `poph agent` /
> `poph instructions` CLI.
> Database and repositories: [`DADOS.md`](DADOS.md). Decisions: [`DECISOES.md`](DECISOES.md).

## 1. What exists now

| Piece | Where | What it does |
|---|---|---|
| Instruction types | `crates/poph-types/src/instructions.rs` | `StructuredInstructions` with the same names, defaults and tolerances as POP Atende (HR-03 §9.1). Tool names are validated on write against the standard list and the organization's HTTP declarations. |
| Composer | `crates/poph-core/src/compositor.rs` | Faithful port of `core/agent/instructions_composer.py`: same output, byte for byte. |
| Repositories | `crates/poph-store/src/repos/agentes.rs` and `instrucoes.rs` | Agent (`V1` fields), agent↔category link, instructions with `If-Match`. |
| CLI | `crates/poph/src/agent.rs` | `poph agent ...` and `poph instructions ...` (text and `--json`). |

The crate `poph-agent` (D-08) does not exist yet. The composer lives in `poph-core` because it is pure code
on top of `poph-types`: it can move to `poph-agent` without changing a line when HR-13 opens that crate.

## 2. Agent fields (`V1`)

The fields are the ones marked `V1` in the agent configuration inventory (history) and were already in the
HR-04b schema. What this task adds is the rule and the entry point:

- **Identity/profile:** `name`, `slug`, `description`, `status`, `agent_type`, `category`.
- **Department:** `default_department_id` (where new conversations go) and the handoff pair
  (`human_handoff_enabled`, `human_handoff_department_id`, gate G1/G4).
- **LLM per agent:** `provider`, `model`, `temperature`, `max_output_tokens`, `max_context_tokens`.
  In POP Atende these fields were saved and ignored; in the Harness they take effect (the difference is
  recorded in HR-03).
- **Turn:** `grouping_window_ms` (grouping window), `max_tool_rounds`, `max_tool_calls_per_message`.
- **RAG:** `rag_top_k`, `rag_min_score` (per agent; in POP Atende they were global).
- **Jev:** `jev_json` (flags and thresholds that override the configuration).
- **Product categories:** link table `agent_product_categories`.

## 3. Rules that change behavior

### D-05 — inactive means inactive

`Agente::pode_abrir_turno()` and `Agentes::obter_para_turno()` apply the decision: only `status = active`
opens a turn. An agent that is `inactive`/`archived` returns `DomainError::AgenteInativo` (with id and
status), not a ready agent. The inactive agent **stays listed** and editable (the Console needs to show
it); it only leaves the turn path.

### D-04 — enabled tool filters for real

`StructuredInstructions::enabled_tools()` is the agent's toolset. The standard list
(`TOOLS_V1`) contains `consultar_base`, `buscar_produto`, `enviar_arquivo`, `transferir`,
`cart_add_item`, `cart_remove_item`, `cart_summary`, `cart_clear`, `fluxo_executar_acao`,
`fluxo_abandonar`, `fluxo_iniciar`, `atendimento_encerrar` and `register_lead`.
An agent can also enable tools from its organization's [HTTP declarations](CONFIGURACAO.md#internal-http-tools).
`register_lead` requires a declaration to run. It is the only HTTP tool available to site conversations
and must be explicitly allowed for that channel.

The CLI and API validate names **on write** against the standard list and the organization's declarations.
Legacy POP Atende JSON with names such as `search_knowledge_base` can still be read and mapped by the
importer (HR-52).

### Hand-edited text is preserved

`agent_instructions.derived_from_json` keeps the distinction from POP Atende: `1` = text generated by the
composer (can be recomposed), `0` = prompt edited by hand (not overwritten without an order).
`poph instructions create|update --file` recomposes; `--markdown-file` saves the text as it is.

## 4. The composer

Port of `compose_instructions`. Fixed order of blocks:

1. **Identity** — only if `identity.name` **or** `identity.company` is set; heading
   `# {nome}, {papel} da {empresa}` (`# {name}, {role} of {company}`, emitted as-is), followed by the company
   description.
2. **Principles** — numbered, each with the fallback sentence when the action is known.
3. **Scope** — `O que voce faz` / `O que voce NAO faz` (“What you do” / “What you do NOT do”). These headings
   are emitted by the code in Portuguese and are kept as they are. The section **does not** emit handoff.
4. **Tone** — always emitted (language, tone, emojis, format, additional restrictions).
5. **Tools** — only the enabled ones, with `— quando usar` (“when to use”) when present.
6. **Additional instructions**.

What it does **not** do (on purpose): `flow_steps` (no effect in POP Atende), handoff, fixed system style,
Cases, date rules and time context. These blocks belong to the turn engine (PRD §6.1) and come after the
stable prefix, never inside it.

### Proven parity and how to regenerate

Fixtures in `crates/poph-core/tests/fixtures/compositor/`: `<nome>.json` (input) and
`<nome>.esperado.txt` (real output of the POP Atende composer). The test
`crates/poph-core/tests/compositor_paridade.rs` compares byte for byte across 9 inputs and covers the edge
cases in §9.3 (identity without name, company without name, disabled tool, `flow_steps`).

To regenerate the references when POP Atende changes:

```bash
cd apps/backend
.venv/bin/python ../pop-harness/crates/poph-core/tests/fixtures/compositor/gerar_referencia.py
```

The script only imports `core.agent.instructions_composer` and calls the same function that
`PATCH /agents/{id}/instructions` calls; nothing in the backend is changed.

## 5. CLI

`--org` (UUID v7 or slug) is global and required for data commands. Agent references accept a UUID v7
or slug within that org. Updates require `--if-match` with the version that was read. Instruction
creation requires that the agent have no instructions yet. Output from `--json` uses the stable
`versao_relatorio: 1` format and omits secrets.

Slug derivation lowercases the name, folds supported accented characters to ASCII, collapses runs of
separators to a hyphen, and caps the slug at 64 characters. When instructions are saved from a manual
Markdown file, the CLI keeps the existing structured JSON, or stores an empty object on first save.
The CLI checks the syntax of `--jev-json` before writing an agent update.

```bash
# create the agent (slug derived from the name: "Bia Atendente" → bia-atendente)
poph --org demo agent create --name "Bia Atendente" --department <dep_id> --model gemini-3.8-flash-tiered

# save the structured instructions (the text is recomposed by the composer)
poph --org demo instructions create bia-atendente --file instrucoes.json

# hand-edited prompt, no recomposition
poph --org demo instructions update bia-atendente --if-match 2 --markdown-file prompt.md

# show the agent, its categories and the composed text
poph --org demo agent show bia-atendente

# deactivate (D-05: stops opening turns)
poph --org demo agent update bia-atendente --if-match 1 --status inactive

# link product categories (replaces the list)
poph --org demo agent update bia-atendente --if-match 2 --category-id <cat_id>
```

Exit codes: `0` success, `1` error (message on stderr), `2` incorrect usage (clap).

While `poph org` does not exist (HR-08), the example `crates/poph/examples/semear_org.rs` creates an org and
a department to exercise the CLI:

```bash
cargo run -p poph --example semear_org -- demo "Org Demonstração"
```

The example uses the default `data/` directory unless `POPH_DADOS_DIRETORIO` is set.

## 7. Turn engine

The [turn lifecycle](TURNO.md) documents grouping, prompts, tools, streaming, and recovery.
The engine first checks the agent, conversation, and channel integration. An inactive agent,
a non-open conversation, or an unavailable channel integration leaves the incoming message
recorded and skips the reply. Website conversations use their own execution path. A
missing stored trigger is also skipped. An error that prevents the engine from reaching
the turn record is returned to the caller. A recorded result carries the turn state,
handled message IDs, text, timing, token usage, and the Jev result when available.
Observers receive events inline and must return promptly.

- **Grouping.** The engine reads up to 200 recent messages by default. It walks backward
  through consecutive inbound customer messages and opens a turn only if that group
  contains the triggering message. The actor completes both the original inbox item and
  the items for the grouped messages, scanning up to 500 pending items for the org.
- **Jev and search.** With G2 enabled, the first batch starts during the grouping window.
  It is reused if the ID of the latest customer message stays the same. The search and
  any fresh Jev batch can run in parallel. A reliable G3 `nada` or an applicable G8
  farewell may allow the turn to stop waiting for search. G3 `nada` also disables the
  knowledge and catalog tools for that turn. G5 validates the selected product against
  the current candidates and suppresses a duplicate catalog lookup. G6 gets its own
  review call and at most one regeneration, which receives the rejected draft and fixed
  guidance without tools. A regeneration failure keeps the original draft.
- **Attachments.** Messages without attachment references skip the attachment lookup.
  The extracted document text, with its untrusted-content marks, comes before images
  from the same message. Attachments that fail to load are omitted. Image limits apply
  to the whole turn, and logs record the omission without exposing binary content.
- **Handoff and farewell.** The handoff risk question can suppress optional guidance
  without blocking the transfer. The G4 choice is checked against a fresh list of active
  departments in the org, with the agent's configured destination as the fallback.
  G7 uses the default neutral text when its configured reply is blank. G8 sends a
  farewell only for a group with one customer message. An empty configured farewell
  is valid, and the engine leaves the conversation state as it was.
- **Flows.** An active execution supplies its current step without a G9 question.
  Without an active execution, permitted flows are sent to the Jev only when G9 is
  enabled for the agent. The fallback catalog is available only on eligible outcomes.
  Every evaluated turn-flow outcome goes into a single G9 metric series. A disabled
  gate or a catalog above the candidate ceiling uses the fallback series.
- **Output and recovery.** The reply and its outbox item are written together. The
  actor retries transient model failures and unavailable slots within the configured
  limit, provided the turn has not already queued output. It completes permanent
  failures and provider refusals without retrying. Rolling summaries run in the
  background after the reply. The turn-end log excludes customer and reply text.
  It omits words containing `@` or at least seven digits and limits the reason to
  160 characters.
